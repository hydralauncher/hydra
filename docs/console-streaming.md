_Last updated: after `9dc24e8be` (HDR10 whole: negotiation, capture, conversion, Main10 + static metadata, and streaming with the display off) — 260 tests green, 11 of them opt-in hardware probes. **HDR10 is confirmed working on the real Moonlight client** (2026-09-14: the client negotiated HEVC + `dynamicRangeMode=1`, the host logged `HDR10 session` / `told the client the stream is HDR10` / `HDR10 conversion: scRGB FP16 2560x1440 -> BT.2020/PQ P010`, and the user reported the client's HDR output correct). §8 keeps the residual limits._

## 1. What this is

A **Moonlight-compatible game-streaming host** built into Hydra Launcher. When enabled, Hydra advertises itself on the LAN (and VPNs) as a GameStream host named "Hydra"; any Moonlight client (Android, Android TV, iOS, PC…) can pair with it, see the **Hydra game library as app entries** (installed games only, with cover art), and launch games that are then captured, encoded, and streamed from the PC with sub-20ms latency targets. Input (gamepad via a virtual Xbox 360 controller, keyboard/mouse via SendInput) flows back from the client.

**Reference protocol implementations** (read-only, use for interop questions):

- `C:\Users\anderson\Projetos\Sunshine` — Sunshine source clone (ground truth for host behavior).
- cgutman/enet (the fork moonlight-common-c vendors) — ENet protocol reference.
- github.com/moonlight-stream/moonlight-common-c — client protocol truth.
- github.com/moonlight-stream/moonlight-android — the client's parsers (strictest XML consumer).

## 2. Architecture

```
Moonlight client (phone/TV — existing app, we build NO client)
   │  mDNS _nvstream._tcp :47989 ──► discovery (srv: native/hydra-stream/src/mdns.rs)
   │  HTTPS :47984 ─────────────────► pair (held-response PIN flow) / applist / launch / resume / cancel
   │  HTTP  :47989 ─────────────────► serverinfo, pair phase 1
   │  RTSP  :48010 ─────────────────► session setup (plaintext + AES-GCM "rtspenc" framing)
   │  UDP   :47998 ◄───────────────── video RTP (H.264, Sunshine-exact NV/FEC wire format)
   │  UDP   :48000 ◄───────────────── audio RTP (Opus)
   │  UDP   :47999 ◄───────────────── ENet control + input return path
   ▼
hydra-stream.exe — Rust sidecar (native/hydra-stream), spawned by Electron,
   stdio newline-delimited JSON-RPC (requests + events both directions)
   ▲
Electron main process (src/main/services/streaming/ + stream-sidecar.ts)
   pref toggle → spawn/kill sidecar; pairing PIN modal; big-picture on Desktop launch;
   game launch via existing launch-game pipeline; game kill via tracked pid on stream end;
   app catalog push (setAppList RPC) with cover downloads.
```

Key design choices:

- **Sidecar, not in-process**: the streaming stack must run at elevated GPU/IO priority and survive Electron hiccups; the stdio JSON-RPC protocol is the only interface (`{"event":"ready","protocolVersion":1}`, methods: `ping`, `submitPairingPin {pin}`, `setAppList {apps:[{appid,title,coverPath?}]}`; events: `pairing-requested`, `pairing-finished`, `session-state`, `client-connected/disconnected`, `launch-requested {appid}`, `stream-ended {appid}`).
- **Whole-display capture** (DXGI Desktop Duplication), not per-window: games launched from Moonlight just appear. The encoder never invents columns: the session's maximum encode size is the captured desktop's width at the _client's_ negotiated aspect ratio (a 3440x1440 21:9 desktop on a 3840x2160 16:9 client is 3440x1936 — the desktop at 1:1 with thin bars, not upscaled and not re-framed), and every _derived_ size below it is macroblock-aligned (both dimensions a multiple of 16), which is what hardware decoders require: the 2026-09-14 iPad session froze on the last frame it had decoded right after the size ladder's first step onto 2580x1452, a size NVENC accepted and VideoToolbox could not decode (the client reported 0% network loss and ~10ms latency throughout — the transport delivered everything). The session's own size — the client's 1/1, e.g. 1920x1080 — is deliberately left on the even grid alone: Sunshine hands the client's width/height to NVENC verbatim and NVENC pads the coded frame to macroblocks itself, so moving that grid would cost rows (1,080 → 1,072) and change the geometry the client asked for, for no benefit.
- **Encoder**: NVENC (RTX) primary, AMF (AMD) fallback, behind a `TextureEncoder` trait; pipelined submit/reap (depth 2) with completion events; async teardown in a detached thread (Sunshine's ASYNC_TEARDOWN).
- **Scaler**: D3D11 VideoProcessor (BGRA staging copy → owned RT targets) — always on; encoders register the owned targets once, never the duplication surface (survives display-mode changes; fast-path recreation recreates only the duplicator when resolution is unchanged: measured <1ms vs ~45–97ms full). The full path is also what the session's ONE startup resolution pays (the encode size is resolved before the first frame and never changes again, see §2's loss-recovery entry): the targets are rebuilt at the resolved size, the encoder session is re-created at it (new SPS/PPS), and the first frame after it is a forced IDR — the client's decoder re-inits on those and needs nothing else.
- **Freshness first**: a captured frame whose _projected_ age — its age now plus the encoder's measured acquire→bitstream latency for the frames already inside it and for itself — is past the freshness budget is never _submitted_ to the encoder. The pipeline skips ahead to the newest desktop texture and, when even that frame is projected past the budget, skips the submission outright, so the encoder's reference chain only ever holds frames that were shipped. This is what stops the client being shown P-frames referencing frames it never received: a live 1080p60 session pinned at the old 0.05bpp floor dropped **163** already-encoded frames, and the artifacts lasted until the next keyframe. The effective frame rate falls instead — the intended degradation below the bits-per-pixel floor, reported as `stale-skipped` (pre-encode, expected to rise). The residual case — a frame only the encode could reveal as late — is still dropped by the sender loop, which now forces the **next frame to a full IDR** and logs `video: dropped frame N after encode: next frame forced to IDR (reference chain would otherwise break)` (metric `dropped-after-encode`, expected zero); the same forcing covers the P-frame-suppression drop and the unknown-endpoint drop. IDRs are exempt from the age gate (the client's recovery mechanism). **P-frame suppression** and the **2000ms periodic keyframe** are the **IDR-only recovery mode**, active when the encoder cannot invalidate reference frames (AMF, or a driver without ref-pic invalidation): while the client is starving (IDR requests within the last 1s), P-frames are held back only until the forced IDR that opened the episode has been _encoded_ (log `video: P-frame suppression OFF (episode IDR sent)`) — with a hard cap of **4 frame decisions** if no IDR ever arrives — so continuous begging cannot keep P-frames off the wire (`HYDRA_STREAM_IDR_QUIET_MS` is the begging-_wave_ boundary that releases the cap and re-arms for a later loss, not the suppression exit), and hygiene IDRs at ≤2000ms bound the corruption lifetime (recovery itself is client-driven: `REQUEST_IDR` is honoured immediately through the starvation gate (`src/stream.rs`), which never answers faster than one IDR per **200ms** (~5/s) and _slows_ to one per **500ms** (2/s) once eight answered requests in one episode are still drawing more — persistent begging is evidence that keyframes are not the fix, not a reason to send more: the 2026-09-14 iPad session begged ~15/s for the whole run and the old 50ms escalation answered ~15/s, 951 forced IDRs of ~95KB each at 3440x1936, ~44% of a 25Mbps stream, and the picture stayed frozen; the host forces no proactive refresh of its own, so an episode's whole keyframe spend is the `idr answered+`/`coalesced+` clause on the control 5s stats — the hygiene cadence is only the bound on damage nobody asked about). An **RFI-capable** encoder turns suppression off (the client resumes at the next recovery frame) and keeps only a 5s safety keyframe.
- **The negotiated frame rate is a hard send cap**: the capture boundary admits one frame per negotiated slot (`FramePacer`), so a 165Hz panel, DLSS Frame Generation, or a game running above the client's `maxFPS` cannot push more frames than the client budgeted for — the surplus presents are dropped at the acquire, before the scaler and the encoder, so they cost neither a scale nor a 4K encode. The gate covers every path that can put a frame on the wire (captured frames, the idle-desktop duplicate keepalive, forced IDRs), the admitted frame is the newest one available at its slot (the duplicator carries a single current desktop image, so nothing stale is ever re-issued), and the 5s latency line reports the result as `sent N/s of <negotiated fps>`. Before this, the session shipped 95-103 fps against a negotiated 60 (measured from `frame_index` deltas): the client's decoder overran, dropped frames, and begged — 672 forced IDRs in 100s, each a 96-103KB keyframe.
- **Loss recovery stack**: Sunshine-exact FEC (nanors Cauchy RS over GF(2⁸) poly 0x11d), per-frame percentage read by the client from fecInfo — base 20% (Sunshine's default), adaptive ladder →30% under congestion (the 20% congestion rung equals the base, so it is a no-op), each block's parity raised to the client's `minRequiredFecPackets` when the percentage falls short (Sunshine `stream.cpp:852-859`, `parity_shards = minparityshards`, the block then reporting the recomputed `(100*parity)/(data_shards)` percentage on its shards); adaptive bitrate (NVENC live reconfigure) that steps down on an IDR flood only when the same window is corroborated by the ENet congestion verdict or a client loss signal (a flood is a symptom of frame loss, never evidence the video rate is too high), and whose ENet verdict needs _material_ retransmit evidence — `>=5` events that are also `>20%` of the reliables received in the window, or `>=30` events outright, where an event is one retransmit **arrival**: a re-send the receive rule refused (`window-drops`) or a re-send of a sequence already seen at the delivery cursor (`dup`). The two counters are different arrivals of the same retransmit pressure, so both are evidence and the verdict sums them — one _sequence_ re-sent across a cursor advance is counted once per arrival (a duplicate while the cursor sat on it, a refusal after a newer command was delivered), which is intended — so a wireless control channel's background re-sends no longer cut a stream the client reports as 0% loss while the windows that really drowned carry 27-95 refusals on top of 20-83 duplicates; floor `max(6000, negotiated/4, pixels×fps×0.072)` per session, so the ladder stops where the encoder can still hold the frame rate with margin (0.072 bpp is the rate at which the one-frame VBV's drain spends ~70% of the frame interval; at the old 0.05 it spent the whole interval, which is why a session pinned there dropped 163 already-encoded frames), and a **resolution decision made once, before the first frame** (frame rate kept): the encode size is the largest of `{1, 3/4, 2/3, 1/2, 2/5, 1/4}` of the session's maximum size (`HYDRA_STREAM_MIN_BITS_PER_PIXEL` decides what the negotiated bitrate pays for; the 1/1 rung is the session's maximum itself — the client's own size, width-capped at the desktop and even-parity only, e.g. 1920x1080 kept verbatim — while every rung below it is macroblock-aligned: the width rounded down to a multiple of 16, the height the nearest multiple of 16 at the client's negotiated aspect, never more than ~1% off it — so no rung can drift into the desktop's shape or onto a size a hardware decoder rejects), resolved before the first frame leaves the host and then FIXED for the session: a mid-stream SPS/PPS change makes an Apple client (VideoToolbox) tear down and rebuild its decoder, which the host sees only as IDR begging (the two measured sessions that resized mid-stream begged 978 and 876 IDRs against 109 for one that never did, with our send side healthy in all three); below the bits-per-pixel floor the frame rate degrades instead, which the client rides out without a decoder re-init — the geometry the session really encodes is reported by the pipeline every adaptive tick, so a client that negotiated `0x0` ("encoder resolves to desktop") is covered too.
- **Sunshine-style sender rate limiting** (900Mbps ceiling, ~12.7µs/packet schedule, ≤46-packet batches, credit carried across frames) — no microbursts; first packet immediate.

8. **Test suite**: 236 tests — unit, socket-level e2e, reference-ENet differential, golden vectors (nanors, GCM vs OpenSSL, NVENC offsets vs compiled C), RFI recovery mode + reference-frame resolution, the Opus multistream layouts (5.1/7.1 encode→decode round-trips), the WASAPI resample decision, the packetizer's negotiated packet duration, the IDR starvation gate (200ms floor, 500ms backoff, an answered-vs-coalesced accounting that can never drop a request), the byte-exact BT.709 VUI colour metadata (H.264 and, via the C-probe-verified `hevcVUIParameters` offset, HEVC), and the loopback live smoke.
9. **RFI end-to-end**: the encoder's reference-frame-invalidation support is probed at startup with a throwaway NVENC session (`capture::probe_recovery_capability`, ref count 5, falling back to 1), advertised in DESCRIBE (`a=x-nv-video[0].refPicInvalidation:1`), the client's `x-nv-video[0].maxNumReferenceFrames` is honored as the session DPB depth (probe depth is the ceiling, 16 the max), and the DPB depth now decides whether RFI is really live — which in turn switches the sender loop to the RFI recovery mode (no P-suppression) with a 5s safety keyframe, while FEC's base rises to Sunshine's 20%.
10. **Surround (5.1/7.1)**: DESCRIBE advertises Sunshine's five `surround-params` rows in `stream_configs` order (stereo 2/1/1, 5.1 6/4/2, 5.1 6/6/0, 7.1 8/5/3, 7.1 8/8/0) with GFE's rotated mapping on the two normal-quality surround rows only, the `/launch` `surroundAudioInfo` channel count (low 16 bits) plus the RTSP ANNOUNCE's `x-nv-audio.surround.AudioQuality` (quality tier) and `x-nv-audio.surround.enable` (explicit 0 pins stereo) select the Opus multistream layout with Sunshine's per-layout bitrates (Sunshine reads all three from the ANNOUNCE — `src/rtsp.cpp:1148-1153`; deliberate here, and §8's backlog records it), and the WASAPI pipeline encodes exactly that layout — the client builds its `opus_multistream` decoder from the advertised string, so a mismatch in either direction means total silence for surround clients.
11. **Build/colour polish (`f22120c14`)**: the vendored Opus is compiled with `USE_ALLOCA` on MSVC and `VAR_ARRAYS` elsewhere (MSVC has no C99 VLAs); the BT.709 limited-range VUI metadata of item 8; new-code de-duplication (`scripts/lib/native-build.cjs`, `src/main/services/child-process-rpc.ts`, shared settings field components); and the six SonarCloud new-code issues.

## 6. Configuration surface (env vars, sidecar)

The ignored live audio probes additionally read `HYDRA_AUDIO_PROBE_SECONDS` (default 5) and `HYDRA_AUDIO_PROBE_KEEPER` (`1` adds the production silence keeper). ## 7. How to test (manual)

1. Quit Sunshine; disable ReLive; `npx electron-vite dev` (toggle streaming ON).
2. Phone on the same LAN (router WiFi — NOT the Windows hotspot; see §8). Moonlight: pull-to-refresh → Hydra appears → tap → PIN shows in Hydra's modal (phone displays it; type into Hydra) → app list = Desktop + installed games with covers.
3. Launch a game: it starts on the PC (existing launch pipeline incl. preflight), streams; big-picture only opens for Desktop; quitting the stream kills the game (pid-verified).
4. Read the dev log: `(stream-sidecar)` lines — `video: recovery mode = rfi`/`video: recovery mode = idr …` (the one line that says whether reference-frame invalidation is live), `latency 5s` (stage percentiles, **`sent N/s of <negotiated fps>` — the sent cadence, which must never exceed the negotiated rate**, bitrate, `stale-skipped` (submissions the pre-encode gate refused — the intended degradation, expected to rise below the bits-per-pixel floor), `dropped-after-encode` (must stay 0: each one logs `video: dropped frame N after encode: next frame forced to IDR (reference chain would otherwise break)` and forces a full IDR) and `p-suppressed` counts), `enet: stats` (dup/window-drops/congestion + 5s deltas, the window line reporting `events+` — the verdict's figure — with its split `= dup+ window-drops+`, the two counters being different arrivals of the same retransmit pressure, both consumed; including the per-channel `discards-behind/ahead[….]` split and the bounded `enet: chN discard #n seq=… cursor=… watermark=…` trace — which of the two discard rules fires on legitimate input traffic is still unknown, so the next session's first 20 discards per channel are the evidence), `adaptive bitrate`/`FEC` transitions, `video: encode size resolved before the first frame: 3440x1936 (bpp 0.058 at 60000kbps; fixed for the session)` (**the one size resolution a session makes — there is no mid-session size change**; `encode size resolution to WxH refused (…); continuing at WxH` if that size cannot be created), `forced IDR #N encoded (… SPS=present …)` + `first shard sent` (IDRs should be rare in `rfi` mode), `P-frame suppression ON/OFF`, `control: IDR applied (answered N, coalesced M)` on every answered request and `control: IDR backoff ON/OFF (… cadence …)` when a starving client's begging outlives eight answers (the control `enet: stats` 5s window carries the same spend as `| idr answered+… coalesced+…`), `peer address migrated`, recreation timings.
5. Moonlight performance overlay (Settings → Video) = client-side ground truth for loss%.

## 8. Known limitations & remaining work

- **Network is the dominant variable**: Windows Mobile Hotspot path drops high-rate UDP catastrophically (PC→phone direction) — do not use it; router WiFi works well; wired PC is the gold standard. The stack now survives minutes of trouble that previously froze it in seconds, but a hard link dropout still ends with the _client_ terminating (its own policy).
- **AMF backend**: implemented + probe-verified but never exercised live (display is on the NVIDIA card; cross-adapter sharing is driver-blocked on this pair). To test: move the monitor to the RX 6600 and stream.
- **RFI**: probed at startup (a throwaway encoder session, so the advertised capability always matches a session the driver really accepted), advertised in DESCRIBE as `a=x-nv-video[0].refPicInvalidation:1`, and the client's `x-nv-video[0].maxNumReferenceFrames` is honored as the DPB depth (0/absent = 5, the probed depth is the ceiling, 16 the max). With a live capability (driver cap + DPB > 1) the sender loop runs the RFI recovery mode: P-frame suppression off, 5s safety keyframe. An encoder without ref invalidation (AMF, or a driver without the cap) reports it, advertises nothing, and keeps the IDR-only mode.
- **Audio FEC**: none (Opus PLC only) — Sunshine emits audio parity; audible degradation under loss, not freezes.
- **Display-mode switching** (not implemented): the pipeline letterbox-scales the desktop into the session's size; Sunshine instead reconfigures the output to the session's resolution _and_ refresh rate and restores it afterwards (`display_device.cpp` builds a `SingleDisplayConfiguration` with `m_refresh_rate = {session.fps,1}`; `video.cpp:1484` `reset_display`). The resolution half is covered from the client's side at session start: the _encode_ size is the largest ladder size the negotiated bitrate pays for — the client's own negotiated size when it fits (width-capped at the desktop and even-parity only, so a 1920x1080 session stays 1920x1080 instead of losing 8 rows), else a macroblock-aligned rung below it — with the frame keeping the client's negotiated aspect ratio, so a client asking for more than the desktop is neither upscaled nor re-framed (the earlier component-wise cap ran the encoder at the desktop's 21:9, which the client stretched into its 16:9 surface) — and it is resolved once, before the first frame, and deliberately does _not_ follow the link afterwards, because a mid-session size change costs an Apple client its decoder. The _cadence_ half is covered too (the capture-boundary gate below): the encode and the wire hold the negotiated fps even though the monitor keeps presenting at its own refresh rate, at the cost of one duplication acquire per surplus present. What stays unimplemented is changing the monitor mode itself (fewer presents to drop, and the display-mode switch the client asks for).
- **fps cap on the encode path** (done, 2026-09-14): the send loop used to encode whatever the compositor presented — the old loop-period comment said "a healthy loop iterates at the desktop present rate", and `AcquireNextFrame` hands back an already-presented frame the moment one exists, so the "acquire-wait since the last emit" pacing never limited anything. A live session's own logs (frame_index deltas) showed 95-103 sent frames/s against a negotiated 60, the client's decoder overran into 978 `control: IDR requested` / 672 forced IDRs in 100s (each a 96-103KB keyframe), and Moonlight's overlay read ~30fps with 0% network drops. Now `capture.rs`'s `FramePacer` admits one frame per negotiated slot at the acquire boundary and drops the surplus presents before the scaler and the encoder (so the surplus costs no encode work — at 4K the encode is the bottleneck); the gate covers the idle-duplicate keepalive and forced IDRs too, the admitted frame is the newest available at its slot (DXGI's duplicator carries a single current desktop image whose updates coalesce — no backlog to drain), and every 5s latency line reports `sent N/s of <fps>`.
- **Audit P2 backlog** (from the Sunshine gap analysis, not yet done): 4MB→1MB send buffer re-evaluation, USO/GSO batching, RTT-adaptive ENet retransmit (fixed 500ms now), preset-derived NVENC config (hand-built config validated because this driver's GetPresetConfigEx is broken), encoder caps probing, SO_REUSEADDR, launch window 300s→~30s, app-exit session end, media startup ping deadline, ANNOUNCE attrs (configuredBitrateKbps), audio channel count taken from /launch's surroundAudioInfo (low 16 bits) instead of the ANNOUNCE attribute x-nv-audio.surround.numChannels that Sunshine reads (src/rtsp.cpp:1148) — equivalent for Moonlight clients (both come from the client's channel setting), but that attribute is not parsed, DuplicateOutput1 + factory IsCurrent(), termination reason codes, plaintext-on-encrypted strictness, control thread priority.
- **Hygiene**: `EnetStats::send_reliable` is a RECEIVE counter (misleading name — documented, not renamed); `stats.last_acked_incoming` uses plain `.max()` (cone-blind across u16 wrap; diagnostic only); the send-path loop busy-spins on near-idle desktops (~40k empty polls/s; a `yield_now` on the empty path would be kinder); the _sent_ frame rate is now capped at the negotiated fps by the capture-boundary gate, but the pipeline still polls the duplication once per surplus present it drops (an acquire + release per surplus frame — cheap next to a 4K encode, not free).
- **HDR10 works end to end, confirmed on a real client.** On this branch (`feature/game-streaming-hdr`) a Moonlight client that negotiates HEVC while the desktop is in an HDR mode gets a real HDR10 stream, with no environment variable involved: `SCM_HEVC_MAIN10` is advertised when the startup probe found an HEVC Main10 session, the ANNOUNCE's `x-nv-video[0].dynamicRangeMode` decides the session (`/launch`'s `hdrMode` is recorded but only Sunshine's virtual display device consumes it, `nvhttp.cpp:501`), the capture asks `IDXGIOutput5::DuplicateOutput1` for the FP16 scRGB surface, `hdr.rs` converts it in a shader pass to BT.2020/PQ P010, NVENC encodes Main10 with `inputBitDepth`/`outputBitDepth = NV_ENC_BIT_DEPTH_10` (SDK 13 dropped `pixelBitDepthMinus8`; bits 11-13 of the HEVC bitfield word are reserved there) plus the Rec. 2020 / PQ VUI and the mastering-display + content-light-level SEI (`outputMaxCll`/`outputMasteringDisplay` bits 23/24 plus the two per-picture pointers, `codecPicParams` +80, `pMaxCll` +120, `pMasteringDisplay` +128), and the host sends the client the `0x010e` HDR mode message carrying the same display metadata. `HYDRA_STREAM_HDR` survives only as a testing override. Evidence: the wire dump ffprobes as `Main 10`, `yuv420p10le`, `bt2020`, `smpte2084`, `bt2020nc`, limited range, with the panel's own primaries/luminance read back out of the SEI (302 nits / 0.0979 nits); the live harness covers the negotiated path (`HYDRA_LIVE_HDR=1`); the real-client run logged `HDR10 session (client dynamicRangeMode=1, hdrMode=true, …)` → `told the client the stream is HDR10 (… 55-byte message)` → `HDR10 conversion: scRGB FP16 2560x1440 -> BT.2020/PQ P010 2608x1200` → `first desktop frame acquired`, and the client's HDR output was confirmed correct. **Residual limits**: HDR needs the desktop in an HDR mode (the HDR path *is* the display's FP16 scRGB surface, so an SDR desktop downgrades to SDR); a client that never asks for 10-bit (no `SCM_HEVC_MAIN10` seen, or H.264 chosen) gets SDR; and HDR is only offered when the startup probe really opened a Main10 session.
- **Codec policy: HEVC only where HDR needs it.** H.264 is the safe codec on every client; HEVC exists here for HDR10 (Main10), and that is the one thing H.264 cannot carry — so HEVC is advertised and negotiated **only while the desktop can actually be captured as HDR** (`capture::hevc_offered`, consulted by the DESCRIBE HEVC marker, `ServerCodecModeSupport` and the negotiation alike). With an SDR desktop the host offers H.264 alone, so a client left on "Auto" is never pushed onto HEVC just to stream SDR; with HDR on, the client's own HDR/10-bit request is what selects HEVC Main10. The reason is a measured client-side one: on an Android TV, at otherwise identical settings (same client, `initialBitrateKbps=100000`, same 2608x1200 request, same FEC), HEVC reconnected **six times in nine minutes with 139 forced IDRs**, where H.264 held a **single session with 22** — the frame rate collapsed. `HYDRA_STREAM_CODECS=h264` still pins a host to H.264 outright, and `HYDRA_STREAM_HDR=1` forces the HDR path — and with it HEVC — for the hardware probes. The consequence for such clients is no HDR: HDR10 is HEVC Main10 and nothing else.
- **Turning the display off still ends capture — `ES_DISPLAY_REQUIRED` does not fix that, and an earlier version of this document said it did.** Measured on the RTX 5070 with the output in DPMS standby (what a monitor's standby leaves, and what the Windows power plan produces): the duplication is created fine but delivers **zero** frames, while GDI still reads a composed desktop. Calling `SetThreadExecutionState(ES_CONTINUOUS | ES_DISPLAY_REQUIRED)` again *while the display is off* does **not** bring capture back — `probe_display_standby_capture`'s keep-alive buckets measured 0 frames across ten seconds of two-second retries — and a running stream behaves the same way: the mid-stream log shows every acquire timing out while the pipeline keeps re-encoding the last texture (`2409 idle-desktop repeats`, `0` new frames), i.e. the stream stays up but the picture freezes. The 530-frame recovery this document previously cited was an artefact of the probe's cursor wiggler: `SetCursorPos` is user input, and user input wakes a display by itself. What `capture::DisplayKeeper` (and the sender loop's own guard, `video.rs:1856`) genuinely buy is stopping the Windows power plan's display *idle timer* from switching the display off mid-stream — `ES_DISPLAY_REQUIRED`'s documented purpose, and Sunshine's use of it (`display_base.cpp:245`) — plus `create_capture`'s single retry for an output that is not enumerated yet on the first pass. **Consequence**: a session that must survive the display being switched off needs a display that stays on — a virtual display driver (the standard headless answer, which Sunshine also only documents rather than ships: a dummy plug or a VDD) — or a capture path that does not depend on the output's scanout, which is unproven here and would need its own probe (whether the desktop keeps updating with the display off at all). Everything below about HDR still holds when the display is on.
- **Display-off, parked: what was ruled out, and where a future attempt should start.** A virtual display cannot be conjured without a driver: `SetDisplayConfig` only configures targets that already exist, IddCx (Indirect Display Driver — what VDD / SudoVDA / Parsec install) is by definition an installed driver, Miracast needs a receiver and its output is not a DXGI-duplicable framebuffer, and RDP's virtual session display cannot be duplicated. Checked on the development machine: two real adapters (RTX 5070 + RX 6600), one monitor, no indirect-display device and no VDD service — so "use one that is already there" was not an option either. That leaves a **hardware dummy plug / EDID emulator** (no driver, no admin; most dongles are SDR-only, which costs the HDR work, and their mode is fixed by their EDID) or **capturing the game's own swapchain** (hook/proxy DXGI Present — needs no display at all, but it is per-API work and anti-cheat reads it as tampering). The one open question that would let a *capture-path* fix exist is whether the composed desktop keeps updating while the display is off; a probe for it was written and **abandoned as inconclusive** — its first mutation moved the foreground window (maximized, so it cannot move) and its second flipped the wallpaper (which that same maximized window covers), so both failed their display-ON control phase and the "desktop did not change" lines it printed are *not* a result. A future attempt must mutate *above* every window (its own `WS_EX_TOPMOST` window moved across a fixed sample region) or sample a region no maximized window covers, and only then believe the standby phase. Whoever revisits this should also expect the launcher to need **output selection** (`capture::try_adapter` takes the first duplicable output today) regardless of which route is chosen.
- **A stream that never acquires a frame is still silent.** With no frame ever captured, the keepalive path (`capture.rs`, `last_texture == None`) emits nothing, logs nothing after the first timeout and never errors — the shape the display-off bug had. The display fix removes the common cause, but a capture path that never delivers should still surface; not fixed here.
- **`CopyResource` cannot report a format mismatch.** `capture.rs` creates the SDR scaler's staging texture as `B8G8R8A8_UNORM` and fills it with `ID3D11DeviceContext::CopyResource`, which returns `()` — so a source of any other format is dropped silently and the encoder is fed whatever the staging texture last held. Verified with a synthetic `R16G16B16A16_FLOAT` source into a `DEFAULT`-usage destination: the destination stays all zeros, while the FP16→FP16 control round-trips exactly. The SDR staging format is only safe because the SDR duplication list requests BGRA alone; the HDR converter checks the source shape explicitly (`HdrConverter::check_source`), which is also what catches the first-duplication-returns-BGRA quirk noted above.
- **Commit status**: the feature is committed on `feature/game-streaming-hdr` — 19 commits ahead of `origin/main`, HEAD `1bd3f010c`. The HDR slices so far are `79468f59b` (negotiate HEVC and encode it), `fd49a146e` (10-bit coded samples: the SDK 13 bit-depth fields and the P010 registration they unblock) and `1bd3f010c` (scRGB→PQ/BT.2020 P010 conversion). The tree is clean except the untracked scratch directories `.tmp-hdr-probe/` (the reference `nvEncodeAPI.h`, the compiled offset probe and the probe bitstream dumps) and `src/hydra_python_rpc.egg-info/`.

## 9. Hard-won protocol facts (do not rediscover)

- Moonlight-Android hardcodes uniqueid `0123456789ABCDEF`; appversion `7.1.431.-1` ⇒ encrypted control stream: **every** control message is a `0x0001` AES-GCM envelope (key = raw rikey; legacy IV `[seq low byte, 0×15]`; J0 = GHASH(IV‖0⁶⁴‖bitlen) for 16-byte IVs — self-roundtrip tests lie, anchor vs OpenSSL).
- **PIN direction**: the CLIENT generates and displays the PIN; the host must hold the getservercert HTTP response open (Sunshine semantics) until the user types it into the host UI. A 400-response design can't work (client waits indefinitely, no retries).
- applist XML must have **zero whitespace** (kxml reports TEXT events → `getLast()` crash); `ServerCodecModeSupport=0` hard-fails the client before RTSP; serverinfo must report `SUNSHINE_SERVER_BUSY` + `<currentgame>` while launching or the client never proceeds to RTSP.
- SETUP's `client_port` is a hardcoded dummy — the video/audio client endpoints come ONLY from hole-punch packets; media sockets are persistent so punches queue across sessions.
- Moonlight never sends RTSP during a stream: session liveness after PLAY belongs to the control channel alone (Sunshine cancels ping_timeout at control connect).
- ENet: flagless headers (no SENT_TIME) are legal; input rides SEND_UNSEQUENCED inside the 0x0001 envelope; the reference ACKs on receipt — any acked-but-undelivered path is a permanent wedge.
- FEC has no negotiation: the client reads the percentage from each frame's fecInfo; parity shards must carry patched frameIndex/multiFecBlocks (the client reads them from parity too).
- The first frame must be frameIndex **1** (client inits currentFrameNumber=1 and rejects 0).
- **Desktop Duplication returns the current desktop image, not a queue of presents**: `AcquireNextFrame` comes back the moment an image is pending (a present faster than the acquire coalesces into that one image, per MSDN's "current desktop image" / dirty-rect coalescing), and `DXGI_ERROR_WAIT_TIMEOUT` means nothing was presented at all. So a wait for the frame interval must gate _before_ the acquire (`capture.rs`'s `FramePacer` slot) — the timeout inside `AcquireNextFrame` cannot pace anything by itself, and an easy-returned frame is never stale, only early.
- **Hardware decoders want macroblocks, not "even pixels"**: NVENC accepts (and emits) any even size, Apple's VideoToolbox wants both dimensions to be multiples of 16 — and a frame it refuses freezes the picture with the transport looking perfect (0% network loss, ~10ms latency, our send side at 60fps with 0 stale drops). Every size this host _derives_ (the ladder rungs below the session's own 1/1 size) is 16-aligned in both dimensions, floor 16x16; the session's own size is the exception and stays exactly what the client negotiated at even parity (1920x1080, not 1,072), because NVENC pads the _coded_ frame to macroblocks and signals an H.264 crop — Sunshine passes the client's width/height through the same way (`src/nvenc/nvenc_base.cpp` sets `encodeWidth`/`encodeHeight` with no alignment step). The 2026-09-14 iPad freeze followed the size ladder's first step onto 2580x1452 (`w%16=4`, `h%16=12`), a size the encoder accepted and the client could not decode.
- **A mid-stream encode-size change is unsafe on Apple clients**: it re-emits SPS/PPS and the client tears down and rebuilds its decoder, which the host sees only as IDR begging. Two measured sessions that changed size mid-stream ended in avalanches of 978 and 876 applied `REQUEST_IDR`s against 109 for a session that never resized, with our send side healthy in all three. The size is therefore resolved once, before the first frame, and fixed for the session.
- **A wireless control channel's retransmits are a background rate, not a congestion signal**: the per-5s ENet windows of the same iPad session read `dup=2/6/9/11` against `recv=49/53/56/58` (4-19%) with the client reporting 0% loss, while the windows that really drowned (our receive window refusing re-sends under input load) carried 27-95 refusals on top of 20-83 duplicates. A down-step needs `>=5` events AND `>20%` of the window's reliables, or `>=30` events outright, where an event is one retransmit _arrival_: a re-send the receive window refused or a re-send of a sequence already seen at the delivery cursor. Both counters therefore feed the verdict, added — they are different arrivals of the same retransmit pressure, and the sum can count one _sequence_ twice when it is re-sent across a cursor advance (a duplicate while the cursor sat on it, a refusal after a newer command was delivered), which is intended: each arrival is its own event, so a window reading `dup=1176` beside ch1's 1176 behind-cursor discards need not be the same 1176.
- GetPresetConfigEx returns DEVICE_NOT_EXIST on driver 32.0.16.1692 — hand-build the config (validated).
- ViGEmBus is deprecated but functional; driver install via winget/NSIS; gamepad injection must run off the network thread.
- `<currentgame>`/`<state>` follow the running game **process**, reported by the launcher's process watcher over a `setRunningGame` RPC — not the Moonlight session. A game started from Hydra's own UI is visible to Moonlight; a dropped session (enet/control loss, RTSP TEARDOWN, pre-RTSP expiry, client TERMINATION) keeps the game running and the host BUSY, so `/resume` adopts it, while an explicit `/cancel` terminates it. A live session still wins the report during its launch handshake.
