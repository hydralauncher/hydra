# Epic catalogue games in Hydra Cloud Saves V2

## Decision and scope

Enable Hydra's own Cloud Saves V2 to back up and restore local save files for games added from the Epic catalogue. Keep the existing `shop = "epic"`, `objectId = "namespace:playableItemId"` identity end to end. This is not an Epic account connection or an Epic Games cloud storage client. The Epic catalogue integration currently has no Epic sign-in, entitlement, installation, or Epic cloud-save credentials.

The API implementation is based on `develop`. The launcher implementation is based on `codex/epic-catalogue-launcher`. Local validation used isolated worktrees and ignored environment files configured for task-only services.

## Baseline research before implementation

### Launcher and catalogue identity

- `GameShop` already includes `epic` (`src/types/game.types.ts:1`). Search and details already accept Epic through shared catalogue filters and the API (`src/shared/catalogue-store-filters.ts`, `src/shared/epic-shop-details.ts`, `src/main/events/catalogue/get-game-shop-details.ts`). Adding a game stores the compound Epic object ID unchanged under a shop-qualified local key and sends it to the Hydra profile (`src/main/events/library/add-game-to-library.ts:35-82`, `src/main/level/sublevels/keys.ts:3-15`, `src/main/services/library-sync/create-game.ts:5-30`). `remoteId` is a Hydra profile row ID, not an Epic AppName.
- A user chooses an executable for an Epic catalogue entry. The current launcher does not import Epic installations, sign in to Epic, or use Legendary. Cloud saves therefore require a selected executable and a discoverable or user-selected save path.
- The V2 path already builds a platform/Wine context, discovers files with the Rust Ludusavi index, calculates a local snapshot, compares it with a remote head and a per-user/environment anchor, and runs a three-way merge. It then either restores, uploads through `prepare-snapshot -> signed PUT -> commit-snapshot`, or asks the user to resolve a conflict (`src/main/services/cloud-save/cloud-save-game-context.ts`, `build-local-game-snapshot.ts`, `analyze-cloud-save-state.ts`, `merge-user-variant-snapshots.ts`, `sync-game-cloud-save.ts`, `upload-local-game-snapshot.ts`, `restore-remote-snapshot.ts`). Prelaunch restore and postexit upload already use the same flow (`src/main/helpers/launch-game.ts:658-779`, `src/main/services/process-watcher.ts:79-97`, `src/main/services/cloud-save/automatic-sync.ts:318-371`). These are the components to reuse.
- The scanner chooses a manifest entry by object ID, Hydra `remoteId`, then title (`native/hydra-native/src/cloud_save/manifest/lookup.rs:36-65`). Rule `when.store` is compared to `shop` (`native/hydra-native/src/cloud_save/path_resolution/applicability.rs:37-53`). The [Ludusavi schema](https://github.com/mtkennerly/ludusavi-manifest/blob/master/data/schema.strict.yaml) explicitly allows `epic`; no new rule engine is needed. A real Epic catalogue ID may still fail title/rule lookup, so coverage must be checked with fixtures.
- Current intentional gates are Steam-only: automatic mode and execution (`src/main/services/cloud-save/automatic-sync-mode.ts:28-38`, `automatic-sync.ts:58-99`), modern desktop and Big Picture V2 controls (`src/renderer/src/pages/game-details/cloud-save-visibility.ts:26-56`, `src/renderer/src/pages/game-details/cloud-save-v2/cloud-save-v2-context.tsx:164-175`, `src/big-picture/src/components/pages/game/game-settings-modal/cloud-tab-visibility.ts:3-13`, `src/big-picture/src/components/pages/game/cloud-save-v2/cloud-save-v2-context.tsx:155-163`), and the restore response validator (`src/main/services/cloud-save/cloud-save-contract.ts:245-257`). Preload, IPC, storage keys, and the V2 transfer engine already pass `shop` and `objectId`.
- Epic currently sees the legacy cloud-save UI. Current API legacy artifact validation excludes Epic (`src/validation/game.validation.ts:350-374`), so this UI is not evidence that Epic backups work today; historical artifacts are only possible if older deployments accepted them. The stored mode reader ignores the V2 bit for all non-Steam shops; simply exposing the V2 toggle would save `true` and then read it back as disabled or legacy. The old Steam migration is intentionally Steam-only (`automatic-sync-default-migration-policy.ts:13-32`).

### API

- Epic discovery publishes a `GameStoreMapping(shop='epic', objectId='namespace:playableItemId')`. Its canonical `GameCatalogue` row can still have Steam as the default shop (`src/services/canonical-games/identity.ts:11-25`, `src/lambdas/epic-catalogue-discover/db.ts:573-670`). The API's Epic details route resolves this mapping; it does not contain Epic cloud-save paths or credentials (`src/games/handlers/epic-shop-details.ts:6-80`).
- V2 prepare/list/delete validation uses `GAME_SHOP = [steam, launchbox]`; `CATALOGUE_SHOP` already includes Epic (`src/constants/game.ts:1-2`, `src/validation/cloud-save.validation.ts:64-68,177-182`). Swagger repeats the old enum (`src/cloud-saves/cloud-saves.controller.ts`). Once input is accepted, prepare, signed R2 upload, commit, restore, and delete are keyed by user/shop/object ID and have no store-specific branch (`src/cloud-saves/cloud-saves.service.ts`). The Prisma active snapshot key is `(userId, shop, objectId)` (`prisma/schema.prisma:1433-1453`). Existing `default` and `opaque-folder` variants cover non-Steam paths; `steam-account` is already rejected unless `shop = steam` (`src/validation/cloud-save.validation.ts:104-109`). No new table, variant, storage prefix, route, or Epic credential flow is justified.
- `/profile/usage/cloud-saves` currently joins snapshot metadata directly to `GameCatalogue(shop, objectId)` (`src/profile/handlers/get-cloud-save-usage.ts:30-52`). It returns null title/icon for an Epic mapping whose canonical row defaults to Steam. `resolvePublishedCatalogueStore` already maps a published Epic store ID to canonical and Epic details, and rejects withdrawn mappings (`src/games/handlers/resolve-catalogue-store.ts:33-58`). `getEpicShopDetailsBatch` exists (`src/games/handlers/epic-shop-details.ts:92-105`), but returns null when a published mapping lacks `EpicDetails` and builds the full shop-details payload; usage needs a canonical fallback and only title/icon.
- The current direct-upload rollout guide says `cleanupCloudSaveStorage` is not scheduled (`docs/cloud-saves-v2-rollout.md:14-19`). It handles pending uploads, garbage collection, deletion leases, and tombstones. Confirm or wire the existing scheduler before scaling V2 use. This is a V2 operational prerequisite, not an Epic-specific cleanup implementation.

### Epic's own cloud saves

Epic's [Cloud Saves developer guide](https://dev.epicgames.com/docs/epic-games-store/services/cloud-save) says the developer enables the feature per product, specifies local PC/Mac save locations and file sync rules, and tests that the launcher uploads after game exit, restores on a later launch, and prompts on divergent saves. Epic's [player support](https://www.epicgames.com/help/c-36624475/c-31754564/a23593886?lang=en-US) confirms that only supported games expose the Cloud Saves feature; its [conflict guidance](https://www.epicgames.com/help/c-202300000001639/c-202300000001735/a202300000011046?lang=en-US) warns that choosing an older copy can lose progress. Open-source [Legendary](https://github.com/legendary-gl/legendary/blob/master/legendary/core.py) reads `CloudSaveFolder` and `CloudSaveFolder_MAC` from Epic game metadata. Its [Epic API client](https://github.com/legendary-gl/legendary/blob/master/legendary/api/egs.py) uses an Epic account token and Epic AppName for Epic's separate save service. Those IDs and credentials are not in Hydra's catalogue integration. Hydra V2 can work for a game even when that game's Epic-native cloud save is unavailable, provided the local save files are found.

## Implementation order

### 1. API contract, then metadata

1. Change only the V2 prepare/list/delete `shop` schemas to the existing `CATALOGUE_SHOP` in `src/validation/cloud-save.validation.ts`. Leave `GAME_SHOP` unchanged because other legacy and game endpoints use it. Keep the existing 255-character object ID bound and the `steam-account` restriction. Do not require a published mapping before accepting an owner-scoped snapshot: current Steam/Launchbox behavior permits a save without catalogue metadata, and a withdrawn catalogue listing must not make a user's save inaccessible.
2. Change the matching Swagger shop enums and describe the Epic compound ID in `src/cloud-saves/cloud-saves.controller.ts`. Update the shop enum and example in `src/profile/profile.controller.ts`. Keep the current auth, Cloud subscription guard, response payloads, and status codes.
3. Make usage metadata mapping-aware in the existing `ProfileService`. Move this one endpoint's business logic out of the Express-style handler and let the controller use the current-user decorator and return plain data, following `docs/nestjs-api-patterns.md`. Add a batch form beside `resolvePublishedCatalogueStore` in its existing file and share its published/withdrawn semantics, avoiding per-snapshot queries and duplicate mapping rules. Prefer Epic-specific title/icon from details when present, then canonical metadata; keep null metadata for missing or withdrawn mappings. Keep snapshot listing and deletion possible regardless of metadata.
4. Add focused tests for Epic prepare/list/delete acceptance; `epic + steam-account` rejection; one Epic prepare/commit/restore/delete identity round trip; Swagger enums; and usage metadata for an Epic mapping whose canonical row is Steam, including missing/withdrawn mapping. Existing generic V2 service tests remain the primary coverage.

### 2. Launcher eligibility and user transition

1. Add one shared V2-enabled-shop predicate for Steam and Epic and use it in main, desktop, and Big Picture gates. Keep `custom` and `launchbox` behavior unchanged. Extend the restore contract's accepted API shop list to include Epic while still rejecting `custom`; retain its existing Steam-only account-variant check. Reuse the mounted V2 providers, IPC, overview, manual sync, conflict, path-approval, deletion, and launch hooks. Do not create an Epic sync engine or new Epic UI tree.
2. Update `resolveStoredCloudSaveAutomaticSyncModeForShop` so an explicit Epic V2 setting is honored. For an absent Epic V2 setting, keep existing legacy-on as legacy and legacy-off as disabled. Make Epic V2 automatic sync opt-in for the initial rollout. The existing atomic mode setter turns legacy off when the user enables V2. Do not rerun or broaden the Steam default migration. Modern and Big Picture settings should show Epic V2 controls. A stored legacy-on flag needs a clear switch before V2 automatic sync begins, even though the current API rejects Epic legacy artifact operations. Manual V2 actions should not race an active legacy automatic job.
3. Allow automatic prelaunch restore and postexit upload for Epic through the existing eligibility and guard paths, after a user enables V2 and chooses an executable. Preserve current safety checks for subscription, deletion pending, game running, environment identity, conflict, checksum, and failed restore. Show the existing path selection flow when no rule yields files; do not report a successful backup for an empty or unresolved scan.

### 3. Save discovery safety and validation

1. Stop passing a configured Steam root into the native Epic path context (`src/main/services/cloud-save/cloud-save-game-context.ts:47-75`). Today `<root>` resolution can scan a Steam installation for an Epic entry (`native/hydra-native/src/cloud_save/path_resolution/resolve_path.rs:139-236`). Keep the existing Steam context unchanged. Validate what the current native `<base>` and executable-derived paths do for Epic games with nested executables; use an existing stored install path if one is available, or user-selected custom paths, before adding a new root model.
2. Build local synthetic Ludusavi fixtures for Epic `when.store`, normal user directories, `<base>`, `<root>`, and `<storeUserId>`. Verify the real catalogue `namespace:playableItemId` plus title lookup against representative Epic games. The native `<storeUserId>` wildcard maps to the existing `opaque-folder` variant and restores that literal folder; this needs a cross-device test when account-specific folders are involved. `<storeGameId>` is in the Ludusavi format but Hydra's token resolver does not implement it. Add substitution only if a selected real rule requires it, with a focused fixture. Do not invent Epic account IDs.
3. Exercise representative Windows, macOS, and Linux/Wine Epic paths with manual path fallback; include an Epic title whose save path is shared with its Steam version. Verify no Steam-root scan, correct file selection, stable environment identity, safe restore, prelaunch conflict handling, and postexit upload. If the Epic Games Launcher also syncs those files, test its ordering with Hydra rather than silently choosing a winner. Hydra snapshots remain separate by shop/object ID; no cross-store merge is implied.

## Rollout and acceptance

- Deploy API validation/Swagger/usage support before exposing Epic V2 in the launcher. No schema migration or maintenance-window write block is needed for the existing variant model. The old direct-upload migration steps in `docs/cloud-saves-v2-rollout.md` are historical and should not be repeated for this change.
- Confirm the existing `cleanupCloudSaveStorage` job runs, and run the target-R2 checksum probe documented in the rollout guide. Then validate the API contract and focused launcher/native fixtures. On API, run the repository's required local lint workflow checks before any push: `pnpm format-check`, `npx commitlint --last --verbose`, `pnpm typecheck`, and `pnpm lint`.
- Release Epic V2 as an explicit per-game choice first. A successful pilot shows an Epic game with a known path can back up, restore to a matching account folder on another environment, detect divergent edits without overwriting either copy, and keep the same `epic:namespace:playableItemId` key through local state, API snapshots, and usage. A game with no detected save files stays unbacked-up and points the user to custom paths. Existing Epic legacy flags remain until the user chooses V2; the mode switch does not delete historical artifacts, if any exist. Steam and Launchbox flows retain their current results.

## Implementation record

- The API now accepts Epic in the existing V2 prepare/list/delete validators and Swagger schemas. The `steam-account` variant remains Steam-only. The current snapshot service, blob storage, auth, and database model are reused without a new route or migration.
- Usage resolution batches store mappings using the same published/withdrawn semantics as game details. It prefers Epic-specific title/icon, falls back to canonical metadata, and keeps snapshots addressable even if their catalogue listing is missing or withdrawn. This endpoint's persistence and metadata logic now lives in `ProfileService`, with a thin NestJS controller.
- The launcher uses one shared Steam/Epic V2 eligibility helper across main, desktop, and Big Picture. An explicit Epic V2 mode survives reload; absent Epic mode stays disabled or legacy according to the existing flag. Switching to V2 atomically disables the legacy automatic flag. The existing V2 screen, scanner, merge, transfer, restore, and launch hooks are reused. Epic legacy backup controls are hidden because the legacy API does not accept Epic.
- The native scanner receives no Steam root for an Epic game and also guards against deriving one from an executable under Steam. This prevents `<root>` rules from reading another store's save tree. Manifest title lookup and `when.store = epic` already provide discovery; opaque account folders and the existing user-selected path flow cover paths that cannot be inferred.
- Epic restore planning requires the account-bearing folder or filename from an `opaque-folder` variant to exist on the destination before writing. A different destination account stays unresolved instead of reporting a successful restore to an unused source account ID. A newly installed game may need one launch to create its account folder before Hydra can restore that variant; there is no automatic cross-account save remapping.
- The mode switch remains available even when an overview scan fails, so a legacy-enabled Epic game can still opt into V2. Manual V2 operations are blocked while Epic is in legacy mode and become available after switching.

## Validation evidence

- Reproduce the isolated API round trip from an API worktree after starting task-only PostgreSQL, Redis, and MinIO services with its ignored local `.env`: `CLOUD_SAVE_EPIC_E2E=1 node --env-file=.env node_modules/vitest/vitest.mjs run -c vitest.e2e.config.ts src/cloud-saves/cloud-save-epic.e2e.spec.ts`. Run the launcher Node suite from its worktree with `TMPDIR=$PWD/node_modules/.cache/epic-v2-test-tmp node --import ./scripts/register-ts-node.mjs --test "src/**/*.test.ts"` after creating that ignored cache directory.
- API: 87 focused unit tests passed. The opt-in `src/cloud-saves/cloud-save-epic.e2e.spec.ts` passed against isolated loopback PostgreSQL, Redis, and MinIO services. It covers two opaque account folders, real signed PUTs, incomplete-commit rejection, restore downloads and checksums, one changed blob with one unchanged blob reused, idempotent commit, stale-version conflict, user/shop isolation, mapping-aware usage, and deletion with a shared blob still referenced by another user. `pnpm format-check`, `pnpm typecheck`, and `pnpm lint` passed; lint reported 25 pre-existing warnings outside the changed files.
- Launcher: the final full Node suite passed **792/792** with `TMPDIR` set to an ignored worktree-local cache directory and filesystem access to that worktree. The first default-`TMPDIR` run had two unchanged custom-path test failures because this macOS machine aliases `/var` to `/private/var`; a later sandboxed run failed to create fixtures inside the new worktree, and the rerun with worktree write access passed. Focused UI tests (40), main-process tests, web and Node typechecks, Electron renderer bundle, **185/185 native Rust tests** with `TMPDIR=/private/tmp`, and the native Electron addon build passed. Big Picture bundles with `--target esnext`; its default target is blocked by an existing top-level-await setting.
- A cross-repository native fixture used [Satisfactory's shared Epic/Steam save directory with account subfolders](https://github.com/satisfactorymodding/Documentation/blob/master/modules/ROOT/pages/faq.adoc), [Sonic Frontiers' Epic account folder](https://egdata.app/items/f31b705084194f53b3b703b2decb0d31), and [INSIDE's Epic save file](https://www.pcgamingwiki.com/wiki/Inside). It discovered two Satisfactory account folders, excluded a Steam-root decoy, changed one `.sav` without changing its size, verified only that file's hash and the snapshot aggregate changed, uploaded it through the compiled native addon to a signed local MinIO URL, and verified the stored bytes and SHA-256. The rebuilt addon also planned restore only for an existing matching Epic account folder; it blocked the missing folder, and accepted a file rule with a glob before the account folder only when that account existed. Sonic Frontiers and INSIDE files were also discovered. Native unit fixtures additionally cover Windows-style paths, Wine, macOS rule applicability, and directory rules with a glob before the account folder. These synthetic fixtures do not replace a pilot with installed games on each OS.
- The broader API suite ran 261 files and 2,115 tests: 252 files passed, 5 skipped, and 4 failed (2,089 tests passed, 21 skipped, 5 failed). The failures are outside this change: one pre-existing artwork deletion assertion, a live Ludusavi manifest fetch timeout, and three subscription tests with September 15/20, 2026 fixed dates now in the past. The existing R2 checksum probe accepts matching bytes against local MinIO and rejects same-size mismatches, but its assertion for R2's `BadDigest` XML code fails because MinIO returns `XAmzContentChecksumMismatch`. Run that probe against target R2 before release.

## Remaining release work

1. Deploy API support before releasing the Epic V2 launcher controls. Run a real-game pilot on Windows and at least one Wine/macOS setup, including a first backup, another-device restore to the same Epic account, divergent edits, and interaction with Epic Games Launcher's own sync if it is enabled for that game. Games such as Satisfactory place Steam and Epic account folders beside each other; with no Epic account sign-in, Hydra cannot infer ownership of every sibling folder from a wildcard rule. [Ludusavi manifest issue #77](https://github.com/mtkennerly/ludusavi-manifest/issues/77) also records Epic paths without a store condition, so filtering solely on `when.store` would miss saves. Check the discovered file list before enabling automatic backup on shared-path games.
2. Verify an hourly invocation of the existing `cleanupCloudSaveStorage` in the deployed environment, or wire it through the API's normal scheduled-job architecture. The repository currently defines and tests the cleanup function but does not schedule it; abandoned uploads and durable deletion/GC rows would accumulate without it. This is a pre-existing V2 rollout requirement, shared by Steam and Epic.
3. Verify the signed checksum behavior against target Cloudflare R2, whose error code differs from local MinIO's. Keep the target-R2 validation result with the release record.
